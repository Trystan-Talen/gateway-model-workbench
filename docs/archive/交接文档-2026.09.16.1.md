## 0.1 本轮交接：修复质量评测「资源对照」风险确认不生效（2026-09-12，`2026.09.11.7`）

### 用户报告的现象

> 「质量评测模块你做了个风险提示，我勾选了点新建任务也一直提醒我不能创建要去风险确认勾选。」

也就是：勾选框显示已勾选、界面状态正常，点「新建」仍被服务端拦回，报「疑似生产环境，请勾选风险确认再提交」。

### 根因（前端按「创建类型」猜闸门，与服务端按「端点」的把关口径脱节）

提交处理（`route_test_ui.py` 内联脚本，`$('submit').onclick`）里用**创建类型**判断要不要走确认逻辑：

```js
if(!isCompareCreate()){ ... if(preflightData.requires_confirmation) body.risk_acknowledged = true }
```

`isCompareCreate()` 的实现是 `createKind.endsWith('-compare')`。质量评测的**资源对照**类型正是 `quality-compare`，
它也满足这个判断 —— 于是整段确认逻辑被跳过，请求体里永远不会带 `risk_acknowledged`。

而它提交到的是**带闸门**的 `POST /quality-tests`，服务端 `require_risk_confirmation()` 照章拦截。
只有**网关**对照才走无闸门的 `POST /comparisons`。

一句话：**判断依据（创建类型）和真正的闸门位置（端点）不是一回事。**

### 改法

判断依据改为**请求实际去向的端点**，与服务端闸门口径一致：

```js
const endpoint = isQualityCreate()?'/quality-tests':isCompareCreate()?'/comparisons':'/tasks';
if(endpoint !== '/comparisons'){ ... if(preflightData.requires_confirmation) body.risk_acknowledged = true }
```

同时去掉了原来 `if(!preflightData && (isQualityCreate()||isGatewayCreate()))` 的窄条件，改成 `if(!preflightData)` ——
只要还没预检过就先预检一次，不靠创建类型去猜哪个端点需要。

### 验证（全部实跑，不是静态检查）

- **真机端到端复现**：本机 Chrome 无头 + Node 内置 `WebSocket`（CDP），隔离实例端口 8898。
  进入质量评测 → 资源对照 → 填两个资源 → 勾选风险确认 → 点「新建任务」，
  断言发往 `/quality-tests` 的请求体带 `risk_acknowledged: true`，不再被 400 拦截。
- **新增回归** `tests/test_ui_submit_gate.py`：把**真实**提交处理与 `readQuality` 放进 node 执行，
  钉住四条路径（质量单次 / 质量对照 / 网关单次 / 网关对照）各自要不要带确认字段。
- **变异测试**：把代码改回修复前，质量对照一例**确实失败**（`True is not None`）—— 是真回归守卫，不是摆设。
- 194 项单元测试通过；`py_compile`、内联脚本 `node --check`、`git diff --check` 均干净。
- 网关浏览器冒烟 `problems: []`、`consoleErrors: []`。

### 顺带改动

- `.gitignore` 补上 `server.log`（运行时产物，之前漏了，会在 `git status` 里出现）。
- 版本号 `2026.09.11.6` → `2026.09.11.7`，用于强制刷新浏览器内嵌页面缓存。

### 遗留边界

- 闸门本身是**服务端**强制的，前端勾选框只是 UX；即使前端再出问题，服务端也不会放行疑似生产目标。
  但反过来，前端漏发 `risk_acknowledged` 会让用户「勾了也没用」，这类**前端与服务端口径脱节**是本次的教训：
  以后凡新增「按端点区分行为」的逻辑，判定条件必须锚在端点上。

## 0.2 本轮交接：质量评测「两个模型得分几乎一样」的根因与区分度层（2026-09-12）

### 用户报告的现象

> 「质量评测我测试了一个任务，deepseek-flash 和 glm-5.3 对照测试，两个模型的得分居然非常接近，
>  那这样质量测评还有什么作用？」

### 根因：测量饱和，不是模型相同

回看那次对照（各 117/120，即 97.5%）：**114 题配对打平，双方各在 3 题上独胜，两侧失败题一个都不重叠**
（glm-5.3 挂在 `instruction_following_03/08`、`robustness_03`；deepseek-flash 挂在 `code_reasoning_07`、
`data_analysis_07`、`robustness_04`），且**全部 24 道「挑战」题的双方都通过**。

也就是说，两者并非能力相同，而是这份卷子在当前题量下**已经测到天花板**：题目被两侧都做对了，
剩下的区分信息只剩 6 道题，而 6 道题里有 3:3 的分裂说明不一致本身没有方向。旧报告的问题是
**把"分数接近"直接呈现成了"两者相当"**，读者无法分辨这是「真接近」还是「卷子没分辨力」。

放大这个效应的还有三件事：二值 0/1 评分没有中间态；每个维度只有 10 题，一道题就动 10 个百分点；
格式失误（比如答案后附自检说明导致严格 JSON 判 0）和能力失误混在同一个总分里。

### 改法

1. **新增 `quality_discrimination.py`**，对照报告固定输出「区分度与敏感性」层：
   - McNemar **精确双侧检验**（只看不一致题），`p=1.0` 在 3:3 时是预期结果，说明方向不显著；
   - 配对差值的 **95% 置信区间**，区间跨 0 就不能宣称一侧更好；
   - **最小可检出差异（设计层面）**：由**总配对数**算出（120 对 → 约 12.8 分），
     与本次观测到多少不一致无关。**刻意不按"观测到的不一致数"算**——那会得出"不一致越少越敏感"的
     反直觉结论，是错的；
   - **逐维度分辨率**：10 题/维 → 一道题 10 分；并给出达到 10% 分辨率所需题量（385）；
   - **饱和标记**：某维度两侧都 ≥99.5 时标出，说明该维度对本次对照已无信息量；
   - **判定分档**：结果完全一致 / 只在少数题上不一致 / 有区分 / 区分度良好。
     「有区分」要求**同时**满足差值达可检出水平 **且** `p<0.05`；只满足其一仍写
     「分数接近，且卷子无法分辨」并写明是哪一项没达到。
   - 报告**从不**把「未检出差异」写成「证明无差异」。
2. **修正事实层计数矛盾**：此前报告出现过「未通过 0 题」而内容类失败为 3 的自相矛盾。
   现在事实层把未通过题数按**互斥三类**（链路 / 格式 / 内容）拆分，三类加总**恒等于**未通过题数，
   并加 `unpassed_cases` 字段，不动任务快照里的 `failed_cases` 语义（`tests/test_quality.py:440` 仍钉住它）。
3. **新增校准卷** `quality_calibration.json`（12 维度 × 2 题 = 24 题，全挑战级），
   **不改动默认 120 题套件**。该校准卷**未经实测校准**，需通过临时指向它单独跑一次，
   用来观察哪些维度在当前模型上仍不饱和，作为后续扩题与调难度的输入。

### 验证

- 新增 `tests/test_quality_discrimination.py`（11 项）：全平局判「无法比较」而不是「等效」；
  完全不重叠的失败集不得被写成等效；单侧全胜被识别；饱和与分辨率下限被标出；
  事实层三类计数自洽；Markdown 必须暴露判定与敏感性数值。
- 校准卷另用一个一次性脚本试跑评分：24 个参考答案**全部通过**、72 个反例**全部失败**。
- **205 项单元测试通过**（10 个测试文件）。

### 遗留边界

- 区分度层检验的是**同一批配对题内的一致方向**，不是长期稳定性：每题每资源仍只跑一次，
  要说明稳定性仍需重复运行（见 0.5 第 2 条）。
- 校准卷的分数与 120 题主套件**不可比**，24 题意味着每题在维度分里移动 50 分，只能看饱和与否。

## 0.4 质量评测：当前实现（重要，与历史记录 2026-09-12 节的说法不同）

历史流水（本文末尾）有一句「质量模块不再把『单资源测试』作为独立的可信度结论入口」。
**这句与当前代码不符，已作废。** 实际实现是：

- 质量评测仍有**两个创建类型**，都是**一等入口**：
  - `quality-single`（**单资源测试**）：记录列表里有独立的「单资源测试」分类；报告标题是「单资源诊断」，
    回答「这个资源自身有什么优势/短板/阻断项、适合什么场景」。
  - `quality-compare`（**资源对照**）：记录列表里有独立的「资源对照」分类；报告标题是「资源选型对照」。
- 两者都是**一条质量测试记录**（`QualityTest`），差别在资源数量（1 vs 2）与报告模式，不是两个独立模块。
- **评分维度**当前是题集里的 **12 个 `category`**（各 10 题，共 120 题），不是历史节里说的
  `core_capability / protocol_compliance / safety_boundary` 三层。那三层**没有实现**（全仓库无该标识符），
  属于未落地的设想，见 0.5。
- **可信参考资源模式**（2026-09-12 落地）：资源对照的参考方可以是
  1. 实时填写的可信资源，或
  2. 复用**同题集、已完成**的历史单资源结果（`reference_reuse_id`，服务端校验题集指纹一致，
     复用时不再请求参考资源，并在报告里标记 `historical_reference` 与原任务编号）。
- **执行协议**：资源对照用 `paired_alternating_v1`（同题配对、逐题交替甲乙先后顺序），
  单资源用 `single_sequential_v1`（按题序）。协议随题集 manifest 冻结进任务配置，
  历史报告展示当时的方法快照，不追溯改写。
- **题目与答案可审计**：创建前可 `GET /quality-suite` 查看全部题目、参考答案、评分器与实际输入长度；
  `GET /quality-methodology` 给出 7 个公开评测框架（HELM / IFEval / LongBench / MMLU-Pro / C-Eval /
  LiveBench / EvalPlus）的「借鉴了什么、没覆盖什么」，并明确**未导入官方数据集、未运行官方评分程序**。

### 分数倒挂的严谨解释（保留，未变）

- 2026-09-11 的 `quality_run_bffe09a71583`：GLM-5.3 得 117/120，DeepSeek-Flash 得 118/120；
  差异仅 1 题，**不是**全局能力结论。
- `quality_run_f72b4a82b931`：DeepSeek-V4-Flash-0731 与 DeepSeek-Flash 都是 117/120，
  说明当前题集**不支持**「名字更新/参数更大必然得分更高」的推断。
- 已知测量风险：部分模型在答案后附自检说明，会在**严格格式题**上判 0 分 —— 那测的是「严格输出协议遵循」，
  不是纯知识能力。该维度**不应删除**，但报告必须标注。
- 少量「精确答案」题（如输出 `3条`、`0元` 这类语义正确但非目标字符串会判错）对「资源作为结构化接口的可用性」
  有意义；若要评价一般对话能力，应另设**语义等价评分层**，不能混进同一个分数。

   拆分必须**有行为验收打底**再生产，顺序见 10.1。

## 1. 项目定位与判断边界

这是一个运行在本机的 OpenAI 兼容接口黑盒测试工作台，包含两个**独立一级模块**：

1. **网关压测**：观察计划调度、并发、客户端完成吞吐、成功率、延迟、排队和错误分布。
2. **质量评测**：使用固定题集逐题检查资源实例的能力、格式遵循、完整性、一致性和可观测错误。

必须遵守的结论边界：

- 计划调度 RPM（每分钟请求数）不是实际完成吞吐，也不是网关承载保证。
- 客户端观测到的完成吞吐不是网关内部真实能力；报告不能写成「网关稳定承载 X RPM」。
- 黑盒质量差异不能证明资源的官方身份、来源或真伪，也不能单凭一次测试判定「掺假」。
- 小样本成功率、p95（95 分位）和评分只描述本次测试窗口，不等于长期稳定性或统计置信结论。
- 没有重复运行、长跑和并行混压证据时，系统不得自动批准正式放量。

## 2. 当前信息架构

```text
产品模块
├── 网关压测
│   └── 测试记录
│       ├── 单次压测          (gateway-single)
│       └── 对照实验          (gateway-compare)
└── 质量评测
    └── 测试记录
        ├── 单资源测试        (quality-single)   ← 仍是一等入口
        └── 资源对照          (quality-compare)  ← 仍是用户报告的 bug 所在
```

两个一级模块不共享任务列表、不共享详情页、不共享新建流程。新建测试使用**右侧抽屉**（`position: fixed`、全高、只允许纵向滚动）。

### 2.1 网关压测记录

- 单次压测：一条 `Task` 记录。

## 5. 网关压测指标口径

### 5.1 三个必须分开的速率

1. **计划调度速率**：调度器计划每分钟把多少请求放入执行队列。
2. **实际开始吞吐**：请求真正开始执行的速度；用于判断调度和排队。
3. **客户端观测完成吞吐**：请求收到最终结果的速度；结束后按完成请求数 ÷ 实际运行时间计算，运行中按近期窗口估算。

近似关系：

```text
客户端完成能力（RPM）≈ 并发数 × 60 ÷ 单请求平均总耗时（秒）
```

例：单请求平均耗时约 9.8 秒、并发 60 → `60 ÷ 9.8 ≈ 6.1 请求/秒 ≈ 367 请求/分钟`。
因此计划设 4800 RPM 只是**调度意图**；并发与响应时间不变时，实际完成可能只有约 367 RPM，且队列持续上升。

### 5.2 计时与停止

- 运行中：前端可做平滑显示，但**不能用轮询间隔冒充真实时间**。
- 完成/停止/失败后：用后端 `finished_at - started_at` 冻结计时。
- 正常完成：等已调度请求全部落盘后结束，不误清空在途结果。
- 停止：只取消**尚未开始**的排队请求；已开始的请求完成后继续写入结果。
- 结果写盘成功后，才增加完成数和分类统计。

## 6. 对照实验报告设计

报告结构为「结论先行、证据随后、方法最后」：

1. **结论先行**：建议动作、结论摘要、适用范围、正式放量是否自动批准（**永远不自动批准**）。
2. **快速读报告**：可比性、证据量、执行顺序、实验进度。
3. **关键指标**：客户端观测稳定完成吞吐、最高完成吞吐、最差成功率变化、最大 p95 变化。
4. **关键发现**：失败、长尾、吞吐停滞等信号（是复测线索，不是根因证明）。
5. **实验组结果**：基准组与各对比组横向表格。
6. **下一步动作**：复测、加档、长跑、重复运行或暂停扩大流量。
7. **证据、可比性与方法**：样本量、压力窗口信号、计划 RPM 与完成 RPM 的定义、串行顺序效应、黑盒能力边界。

### 6.1 结论状态

- `pending`：实验未完成，不生成最终判断。
- `hold`：出现明显退化，先定位并复测。
- `review`：存在关注信号，不能直接放量。
- `observe`：当前窗口未观察到明显退化，但不足以支持正式放量。

`decision.formal_release_allowed` **固定为 `false`**；正式准入仍需人工决策和额外证据。

### 6.2 可比性

```json
{
  "comparability": {
    "level": "comparable|partial|not_attributable",
    "label": "可比|部分可比|不可单独归因",
    "changed_dimensions": ["并发上限"],
    "sample_size_changed": false,
    "note": "..."
  }
}
```

判定规则：

- 只改一个压力变量、请求条数相同 → `可比`。
- 只改一个压力变量、请求条数不同 → `部分可比`。
- 同时改并发和计划调度速率 → `不可单独归因`。
- 没改压力变量 → 只能作重复观测，不能解释压力变量影响。

### 6.3 压力窗口信号

代码保留旧字段 `capacity_inflection`（容量拐点）仅供历史兼容，前端只展示 `pressure_window_signal`（压力窗口信号）。
它是**启发式提示**，触发条件包括：压力提高后完成吞吐没增长、成功率下降、总耗时 p95 明显上升。
**这不等于「容量上限」**，需更多档位、重复运行、长跑和并行混压验证。

## 10.1 前端拆分：为什么还没做，以及怎么做才安全
